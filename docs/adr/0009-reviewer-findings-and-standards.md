# 0009. The reviewer reports findings on changed files, applies project standards and is asked again for a missing verdict

Status: Accepted

Context: In Mullet's own ledger, 23 of 40 failed attempts were G7 blocks of real defects, each costing a whole attempt. The reviewer did not check that new behaviour had a test, its reasons were free text passed straight to the next attempt, it never saw the project's coding standards, and a review that ended without a verdict paused the whole job.

Decision: In `mullet/jobs/review.py` the reviewer prompt also asks that new or changed behaviour has a test that would fail without the change, that edge cases the step's goal or acceptance checks name are handled, and that new code has no secrets or injection. It still blocks only for a specific defect it can name, and it still can't pass a node, only block one. `REVIEW_SCHEMA` adds `findings: [{path, line?, problem}]` beside `reasons`. `split_findings` reduces a finding's path to the repo-relative one (an absolute path in the clone's work dir, as given or resolved, and a leading `./` are stripped) and drops one that leaves the clone or holds a control character. Findings on files the change didn't touch are counted (`findings_dropped`) and passed on as reasons marked "(file not changed)". The rest are rendered one line each as `path:line: problem`, capped at `MAX_FINDINGS` and `MAX_FINDING_CHARS`. The feedback always carries the reasons, before the findings so the feedback's length cap can't cut them off (`runner._feedback_text` labels both as the reviewer's words). The optional profile setting `review_standards` (`mullet/jobs/profile.py`) names a repo-relative Markdown file. `read_standards` reads it from the job's base commit, never the work tree or a later step's commit, caps it at `MAX_STANDARDS_CHARS` and shows it to the reviewer only, fenced with the call's random marker as data. A missing, symlinked, binary or empty file is ignored with a note in the gate details. A review that finished on its own but left no structured verdict, and left a session, is resumed with `REASK_PROMPT`, asking only for the verdict, up to `jobs.reask_attempts` times (`mullet/jobs/settings.py`, default 1). A review cut off by its turn limit or its clock (any ending the executor reports as an error) is never asked again: it may have stopped halfway through reading, and "answer now" would get a verdict on partial reading, so it pauses the job as before. An approval given only when asked again is marked `reasked`; on a step whose review is forced for safety (a one-way step, or a risky one in a ladder job) it does not pass, and the job pauses for a person (see ADR 0008). A block given when asked again still fails the attempt, since blocking is the safe answer. The Claude executor's `ask` gains `persist` and `resume` for this, and the runner keeps reviewer sessions only while re-asking is on.

Consequences: The next attempt gets precise, located feedback and none about files it never touched. A worker can't edit the standards its own reviewer applies. Workers never pay for the standards in their prompts. Re-asking is not only a saving: a verdict given when asked again comes from a session that has already ended once, so it is trusted less. It is used only where the review completed and merely left out its JSON, and never to approve a step that is hard to undo. A reviewer that runs out of turns still pauses the job. Reviewer sessions now leave a Claude Code session file behind while re-asking is on. A block whose findings all name unchanged files still blocks, with its reasons and those findings as feedback.
