# 0011. Docker and Podman run each command in a hardened, throwaway container

Status: Accepted

Context: ADR 0007 reserved `docker` and `podman` for a second sandbox backend, for Linux machines without working user namespaces and, later, macOS. A container runner is only worth having if it keeps every 0007 guarantee, and the usual way of running one does not: `-e KEY=value` shows in `ps` and `docker inspect`, a pulled image is whatever the registry serves, and killing the `docker run` client with SIGKILL leaves its container running (checked on Docker 29.9.2).

Decision: `ContainerBackend` (`mullet/jobs/sandbox_backends/container.py`), as `DockerBackend` and `PodmanBackend`, runs each command with `docker run --rm --interactive --sig-proxy=true --name mullet-sbx-<pid>-<random> --label mullet.sandbox=1 --label mullet.owner=<pid> --label mullet.owner.uid=<uid> --label mullet.owner.start=<start in clock ticks> --label mullet.boot=<boot id> --label mullet.host=<machine id> --pull never --log-driver none --user <uid>:<gid> --cap-drop ALL --security-opt no-new-privileges --read-only --ipc private --pids-limit <sandbox.pids_limit> --memory <sandbox.memory> --memory-swap <same>`, plus `--network none` unless the spec asks for network (setup gets the engine's default network: the internet, not the host's loopback). /tmp, /run and $HOME are empty tmpfs; only the spec's paths are bind-mounted, at their own paths, writable ones read-write and the rest read-only. A writable path or overlay that is a symlink is refused, as bubblewrap refuses it, and so is any mount with a symlinked component inside a writable path (a command could have planted one between runs, and the root daemon follows it); this is checked when the argv is built, and the bind sources and targets exactly as the argv hands them to the engine are checked again just before the client starts (resolving the spec's paths again could land somewhere else than the string the daemon gets). Rootless Podman adds `--userns keep-id` so files in the clone stay yours. The image is `sandbox.image` (default `mullet-sandbox:<version>`), built locally by `mullet sandbox build-image` from the shipped Dockerfile, whose base is pinned by digest; it is never pulled.

The entrypoint is `/usr/bin/env -i /usr/bin/python3 -I -S -c <pid1.py> merged|split <command>`, so the container's PID 1 is Mullet's own init, `mullet/jobs/sandbox_backends/pid1.py`, started from an empty environment, in place of `--init`. Its source travels on the command line, so the image needs only Python, and a labelled image from an earlier Mullet still runs this version's init. PID 1 reads the `build_env` variables from stdin as one JSON line (no value is on any command line or in the container's configuration; Mullet writes it once the client runs, with a 30 s deadline, since a pipe can be smaller than the payload), refuses (exit 125) an environment execve can't take (an empty name, `=` or NUL in a name, NUL in a value, a non-string), makes itself non-dumpable, starts the command with stdin on /dev/null (the forked child never returns into PID 1's code: whatever exec raises, it says why and exits 127 when the command isn't found, 126 otherwise), reaps zombies, and forwards TERM, INT, HUP, QUIT, USR1 and USR2 to the command's processes. The rest of stdin is a lifeline: Mullet holds the pipe's write end, and when Mullet dies or the client is killed, the container's stdin closes, and PID 1 kills every process in the container and exits, which ends it.

What covers what when things go wrong:

- Mullet dies (crash, `os._exit`, SIGKILL): the lifeline closes, PID 1 kills everything and exits. A process in the container can't stop this. The kernel never delivers SIGKILL or SIGSTOP to a PID namespace's init from inside it, and other signals only where init has a handler (PID 1's handlers only forward or wake its loop). PID 1 is non-dumpable, so the command, though it has the same uid, can't ptrace it or read `/proc/1/mem`, `/proc/1/environ` or `/proc/1/fd`, even where `kernel.yama.ptrace_scope` is 0.
- The client is killed or ends on a signal, or a run passes its timeout: the client's group gets TERM (passed on to PID 1), then KILL, which closes the lifeline. `docker rm --force <name>` follows too, in case the client never told the daemon.
- The lifeline is lost without reaching PID 1 (a wedged client, a daemon restarted mid-run): `reap_orphans` is the backstop. It removes, with `rm --force`, every `mullet.sandbox=1` container named `mullet-sbx-*`, of this user (`mullet.owner.uid`) on this machine (`mullet.host`), whose owner is gone: another boot, no process with that pid, or one whose start differs. The start is field 22 of `/proc/<pid>/stat`, clock ticks since boot, compared exactly; psutil's `create_time` adds the boot time the kernel derives from the wall clock, so a clock step (NTP, a resume) moved it and made a live owner look gone. The uid label matters on a shared root daemon: with /proc mounted `hidepid=2` another user's live Mullet is invisible, so its pid looks gone. The name matters because `docker commit` copies a sandbox container's labels into the image and so into every container started from it. Without `/etc/machine-id`, `mullet.host` is the hostname, the uid and a random id kept in Mullet's state directory (`sandbox-host-id`, or a hash of that directory's path when it can't be stored), since WSL2 distros on one Docker Desktop daemon share a hostname. Runner start and resume (through `children.kill_stale`), `mullet job stop` (after it has signalled the runner) and `mullet doctor` call it; each engine call gets at most 5 s and the whole reap 15 s, so a wedged daemon can't hold them up, and it never raises. Containers of live owners, of other users or machines sharing a daemon, and from before these labels existed (2.3.0 and the first 2.4 development builds) are left alone. The runner's `runner.pid` and `children.json` record the same start in ticks with the boot id, for the same reason.

`check()` refuses off Linux, without the engine, with an unreachable daemon, with a daemon that has no seccomp (Docker's `SecurityOptions` without a seccomp profile or with an unconfined one, Podman's `SECCOMPEnabled` false), or without the image (naming the build command) or with an image that lacks the labels `org.opencontainers.image.title=mullet-sandbox` and `mullet.sandbox.version` (an image `FROM mullet-sandbox` inherits them). Otherwise it starts a real probe container that must write a file owned by your uid and report, from `/proc/self/status`, `Seccomp: 2`, a zero `CapEff` and `NoNewPrivs: 1`. `auto` tries bubblewrap, then docker, then podman.

`nested_argv` raises `SandboxUnavailable` and `nested_check` is false. A second, network-less sandbox inside the container needs new user and network namespaces, which Docker's and Podman's default seccomp and AppArmor profiles refuse; allowing them means loosening both, so Mullet doesn't. The opencode worker is therefore refused on these backends (`check_runnable` names the backend); checks, gates and setup run under them, and the Claude worker uses Claude Code's own sandbox either way.

Consequences: Commands see the image's userland, not the host's: a repo whose checks need other toolchains needs its own image (`FROM mullet-sandbox`) in `sandbox.image`, and it must keep `/usr/bin/python3` for PID 1. Each command costs a container start, about 0.2 s here with a warm engine. The image labels keep an unrelated image that happens to carry the tag from being used; they are not a signature, and a deliberately forged image would pass. The path checks run just before `docker run`, but the daemon resolves the paths a moment later; nothing sandboxed runs in the clone in between, so only a host process could race it. A cgroup OOM kill can pick PID 1, which ends the container: that fails closed. PID 1's wakeup pipe is set with `warn_on_full_buffer=False`, so a SIGCHLD flood that fills it can't make PID 1 block writing warnings to stderr. Containers started before the uid and tick labels existed are never reaped and must be removed by hand (`docker rm -f $(docker ps -aq --filter label=mullet.sandbox=1)` once no job runs). The digest pin needs moving by hand to pick up Debian security updates. Running opencode under a container would need a sibling container per attempt for the worker's shell (no network, no proxy socket, the clone shared) and a command channel between the two; that is not built. macOS stays refused until the contract tests pass there. The `test_contract_*` tests run against docker, and the `docker-sandbox` CI job builds the image and runs them with `MULLET_REQUIRE_SANDBOX=docker`, which turns a skip into a failure. Podman passes the unit tests only: no machine here has it.
